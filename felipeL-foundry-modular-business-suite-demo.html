Module registration

# each future module (AI, PDF builder, inventory...) # registers itself, the shell never hardcodes a module list class FinancialDashboardModule(BusinessModule): slug = "financial_dashboard" nav_icon = "chart-line" def register(self, app_shell): app_shell.add_route(self.slug, self.build_view()) app_shell.add_nav_entry(self) # app startup, unaware of which modules exist for module in discover_modules("modules/"): module.register(shell)

Data engine abstraction
Same query layer, SQLite today, SQL Server on rollout
# business logic calls the repository, never raw SQL def monthly_revenue(repo, month): return repo.aggregate( "invoices", sum_field="total", month=month ) # the engine swaps in config, not in code repo = RepositoryFactory.build( engine="sqlite" , or "sqlserver" for the network rollout )
This is the real technical risk in a desktop app like this: if calculations and queries are written straight against SQLite syntax, moving the same business to SQL Server later means rewriting the data layer, not just changing a connection string.
